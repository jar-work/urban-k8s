# VM de desarrollo — k3s + Cloudflare Tunnel

## 1. Instalar k3s

```bash
curl -sfL https://get.k3s.io | sh -
```

Verificar:

```bash
sudo k3s kubectl get nodes -o wide
sudo k3s kubectl get svc -n kube-system traefik
```

El nodo debe quedar `Ready`, y el Service `traefik` en `kube-system` debe aparecer como `LoadBalancer` con la IP del propio nodo como `EXTERNAL-IP` (así es como k3s expone Traefik en un nodo único, vía su ServiceLB interno).

Kubeconfig del cluster queda en `/etc/rancher/k3s/k3s.yaml` (root-only).

Para hacer `k9s` (si se instala) hay que hacer un symlink a ese archivo

```bash
sudo mkdir -p /root/.kube
sudo ln -s /etc/rancher/k3s/k3s.yaml /root/.kube/config
sudo k9s
```

## 2. Cloudflare Tunnel — exponer el cluster sin abrir puertos

Todo el tráfico entra por un único túnel saliente hacia el borde de Cloudflare, que reenvía a Traefik dentro del cluster. Traefik sigue haciendo el ruteo fino por hostname a cada Ingress. Ver sección 4 para el estado final recomendado (`cloudflared` corriendo *dentro* del cluster, gestionado por ArgoCD); esta sección documenta el setup inicial que se usó para validar el túnel — un proceso `cloudflared` suelto en el host de la VM, con su propia configuración local, corrido a mano.

### 2.1 Instalar cloudflared

Se usa el `.deb` de GitHub directo (arm64) en vez del repo apt de Cloudflare, porque este último no siempre tiene el codename de una versión de Ubuntu muy nueva:

```bash
curl -L --output cloudflared.deb https://github.com/cloudflare/cloudflared/releases/latest/download/cloudflared-linux-arm64.deb
sudo dpkg -i cloudflared.deb
cloudflared --version
```

### 2.2 Login y creación del túnel

```bash
cloudflared tunnel login
```

Abre un link (no hay navegador en la VM — copiarlo y abrirlo en otra máquina) y pide elegir la zona (`urban-experiment.com`). Solo autoriza al cliente local a operar sobre esa zona — no toca ningún registro DNS existente.

```bash
cloudflared tunnel create k3s-urban-dev
```

Guarda el `TUNNEL-ID` y un archivo de credenciales en `~/.cloudflared/<TUNNEL-ID>.json`.

### 2.3 Convención de hostnames

**Importante:** usar subdominios de un solo nivel bajo la raíz, tipo `<app>-dev.urban-experiment.com`, no anidados (`<app>.dev.urban-experiment.com`). El certificado gratuito de Cloudflare (Universal SSL) solo cubre el dominio raíz y un nivel de wildcard (`*.urban-experiment.com`) — un hostname de dos niveles como `algo.dev.urban-experiment.com` no queda cubierto por ningún certificado y falla con `ERR_SSL_VERSION_OR_CIPHER_MISMATCH` / "This hostname is not covered by a certificate" en el dashboard.

Con el esquema de un nivel, cada app nueva necesita su propia ruta (no hay wildcard de DNS válido para un sufijo parcial como `*-dev.urban-experiment.com`), pero es un comando único por app, no algo que se repite seguido:

```bash
cloudflared tunnel route dns k3s-urban-dev <hostname>
```

Esquema para dev / prod:

| Servicio | Dev | Prod (futuro, VPS) |
|---|---|---|
| Frontend `urban-insights-hub` | `insights-dev.urban-experiment.com` | `insights.urban-experiment.com` |
| API `urban-insights-hub-api` | `insights-api-dev.urban-experiment.com` | `insights-api.urban-experiment.com` |
| Frontend `participatepro` | `participate-dev.urban-experiment.com` | `participate.urban-experiment.com` |

Para prod, no usar wildcard en la raíz del dominio sin auditar antes qué registros ya existen ahí (ya hay al menos uno en uso: la API actual).

### 2.4 Smoke test (validado)

Se probó el túnel con un pod `traefik/whoami` (devuelve headers/hostname recibidos, útil para confirmar que el tráfico atraviesa todo el camino):

```bash
sudo k3s kubectl create deployment whoami --image=traefik/whoami --port=80
sudo k3s kubectl expose deployment whoami --port=80 --target-port=80 --type=NodePort
```

En este punto `cloudflared` corría como proceso suelto en el host de la VM (no dentro del cluster), por lo que **no** podía resolver nombres DNS internos de Kubernetes (`*.svc.cluster.local` — eso solo lo resuelve CoreDNS, conectado al `/etc/resolv.conf` de los Pods, no al del host). Por eso el `config.yml` de esta prueba apunta al NodePort del Service en vez de al nombre DNS interno:

```yaml
# ~/.cloudflared/config.yml
tunnel: <TUNNEL-ID>
credentials-file: /home/ubuntu/.cloudflared/<TUNNEL-ID>.json

ingress:
  - hostname: hello-dev.urban-experiment.com
    service: http://localhost:<NODEPORT>
  - service: http_status:404
```

```bash
cloudflared tunnel route dns k3s-urban-dev hello-dev.urban-experiment.com
cloudflared tunnel run k3s-urban-dev
```

Resultado: `curl https://hello-dev.urban-experiment.com/` devuelve la respuesta del pod `whoami`, con headers `Cf-Connecting-Ip`, `Cf-Ray`, `X-Forwarded-Proto: https` confirmando el recorrido completo por el borde de Cloudflare.

Este setup (proceso en el host) es solo para la prueba inicial — no sobrevive a un reinicio de sesión SSH ni está gestionado por systemd/k8s. El estado final es la sección 3.

## 3. Pendiente: mover cloudflared adentro del cluster

En vez de un proceso suelto en el host de la VM, `cloudflared` debe correr como `Deployment` dentro del cluster, apuntado directo al Service de Traefik (`traefik.kube-system.svc.cluster.local:80`). Ventajas: sobrevive a reinicios/desconexiones de SSH (lo gestiona k3s), puede resolver DNS interno sin rodeos de NodePort, y queda versionado como manifiesto en vez de configuración manual en la VM.

Manifiestos de referencia (ajustar namespace/nombres según se defina el resto del repo):

```yaml
apiVersion: v1
kind: Namespace
metadata:
  name: cloudflare-tunnel
---
apiVersion: v1
kind: Secret
metadata:
  name: cloudflared-credentials
  namespace: cloudflare-tunnel
type: Opaque
stringData:
  credentials.json: |
    # contenido de ~/.cloudflared/<TUNNEL-ID>.json
---
apiVersion: v1
kind: ConfigMap
metadata:
  name: cloudflared-config
  namespace: cloudflare-tunnel
data:
  config.yaml: |
    tunnel: <TUNNEL-ID>
    credentials-file: /etc/cloudflared/creds/credentials.json
    ingress:
      - hostname: insights-dev.urban-experiment.com
        service: http://traefik.kube-system.svc.cluster.local:80
      - hostname: insights-api-dev.urban-experiment.com
        service: http://traefik.kube-system.svc.cluster.local:80
      - hostname: participate-dev.urban-experiment.com
        service: http://traefik.kube-system.svc.cluster.local:80
      - service: http_status:404
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: cloudflared
  namespace: cloudflare-tunnel
spec:
  replicas: 1
  selector:
    matchLabels:
      app: cloudflared
  template:
    metadata:
      labels:
        app: cloudflared
    spec:
      containers:
        - name: cloudflared
          image: cloudflare/cloudflared:latest
          args:
            - tunnel
            - --config
            - /etc/cloudflared/config/config.yaml
            - run
          volumeMounts:
            - name: config
              mountPath: /etc/cloudflared/config
            - name: creds
              mountPath: /etc/cloudflared/creds
      volumes:
        - name: config
          configMap:
            name: cloudflared-config
        - name: creds
          secret:
            secretName: cloudflared-credentials
```

Pendiente al aplicar esto:

- [ ] Fijar la versión de la imagen `cloudflare/cloudflared` (no `:latest`) una vez decidido el pipeline de imágenes.
- [ ] Borrar el hostname de prueba (`hello-dev.urban-experiment.com`) del DNS de Cloudflare y del `config.yaml` una vez migrado.
- [ ] Borrar el Deployment/Service `whoami` de prueba (`kubectl delete deployment,svc whoami`) — no afecta al certificado TLS de Cloudflare (ver nota abajo), es limpieza de scaffolding nomás.
- [ ] Matar el proceso `cloudflared` que corre suelto en el host de la VM (`pkill cloudflared`) una vez el Deployment esté validado, para no tener dos túneles compitiendo.
- [ ] Reemplazar los hostnames de ingress por los reales una vez existan los Ingress de cada app (`urban-insights-hub`, `participatepro`).

**Nota sobre el certificado TLS:** el certificado que cubre estos hostnames es el wildcard gratuito de la zona (`*.urban-experiment.com`, Universal SSL) — es un recurso a nivel de zona, no está atado a que exista un Pod, Service o registro DNS específico. Borrar el pod `whoami` (o cualquier pod) no afecta el certificado para nada. Si además se borra el registro DNS de un hostname de prueba, tampoco hay que tocar nada relacionado a certificados en Cloudflare — es un paso de limpieza de DNS, no de TLS.
